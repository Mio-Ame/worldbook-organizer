Actually tracing the correct order: tapping the trigger first hits the old onGlobalDismiss, which sees the overlay detached, calls the old closePicker, and removes the `is-open` class before the new picker even opens — so that's fine. Then the click opens the new picker and adds `is-open` back, meaning the new early-detachment check actually resolves the ordering issue.

But the keyboard path is still problematic since there's no pointerdown to trigger cleanup early — the stale listeners linger until the next event, so the first pointerdown inside the new popover fires the old onGlobalDismiss, which again finds the overlay detached and removes `is-open` while the new picker is open, causing a cosmetic chevron glitch. The old closePicker also runs `flushPinDirtyOnClose`, which if the pin is dirty triggers a cascade of filter and editor re-application while the new picker is open — not ideal but survivable, along with a harmless `cancelScrollRestore` call from the stale closure.

The cleanest fix is to have `openMobileEditorPickerSheet` check for a stale `_closeMobileEditorPicker` closure (one where the overlay no longer exists) and invoke it before opening, releasing its listeners and observer — a one-line fix that also covers the keyboard-open path and partially addresses the README's concern about externally-removed overlays leaving dangling closures, since it cleans them up at the next open.

All the remaining external-removal paths now route through closePicker, leaving only third-party/host code as a residual low-severity case worth noting with a cheap fix. Shifting focus now to a more important point: the blur evidence turns out to be non-discriminating on Chromium.

Looking at the red run on HEAD, the test asserting blur only fires on the local input before removal still passed with blurCount 1 and connectedOnBlur true — meaning HEAD already dispatches blur on the input while connected during close, likely because Chromium fires blur-on-removal natively. So the five action tests' blurCount: 1 assertions probably pass on HEAD regardless, meaning they don't actually validate that the explicit blur call is effective or necessary. The keyboard residual issue can't be confirmed in this Edge/Chromium environment — it needs WebKit or an actual Android device, since if the user's on Android Chrome/WebView where blur already fires on removal, adding an explicit blur likely wouldn't change keyboard behavior at all.

Which makes me reconsider B03's keyboard residual as possibly unrelated to blur timing — it could instead be that the overlay is visually hidden but not removed, or that focus remains in an input that's still connected but scrolled/positioned off-screen, so the dropdown appears to vanish while the input keeps focus and the keyboard stays up. That matches my earlier R0 A-09 case 2 scenario. I'm tracing through the popover positioning logic using visualViewport offsets to compute effective top/bottom bounds and to set the bottom style when opening above — since the popover uses fixed positioning, which is anchored to the layout viewport, not the visual viewport. On iOS when the keyboard opens, the layout viewport doesn't shrink but the visual viewport does and scrolls, so a fixed element computed using visualViewport offsets could end up mispositioned relative to what's actually visible on screen.

Since the batch doesn't claim to fix B03's root cause, and getBoundingClientRect's viewport relativity gets murky with zoom, I'm concluding this is still an open question rather than something the blur fix addresses — the README itself says the disappearance root cause hasn't been reproduced, so I shouldn't treat the blur change as resolving it.
